# CareKitchen｜安全、資料最小化與風險控制

> 本機版以分頁狀態保留條件和對話，採買摘要經預覽後由使用者複製。公開分享與部署的政策及驗收門檻列於下方。

目前 API 驗證來源、JSON 格式、請求大小、schema、模型輸出和執行程序限流。金鑰只在伺服器。啟用 OpenAI 會送出本輪訊息及必要的規劃條件，請使用虛構案例並避免輸入識別資料；本機規則只會攔截部分格式明顯的聯絡方式或證件號碼。

## 1. 風險分級

| 風險 | P0 政策 | 測試情境 |
|---|---|---|
| 藥物／臨床飲食問題 | 不做相容性或治療判定，提示專業確認 | CK-T22／T26／T27 |
| 明確排除食材被忽略 | 伺服器端保留硬限制，輸出卡重新檢核 | CK-T16／T21／T23 |
| 價格／營養幻覺 | 成本按使用者輸入的單位價格由程式重算；未知維持未知 | CK-T11～T15 |
| 對話意外曝光 | 預設私有，公開需預覽、同意、去識別，唯讀 token／到期／撤回 | CK-T30 |
| 未授權讀取 session | 不可用 URL sessionId 任意讀取，owner session / capability 嚴格隔離 | 人工越權測試 |
| API Key 外洩 | 只能在可信伺服器環境變數，client 與 Git 不接觸 | 靜態掃描與瀏覽器檢查 |
| Prompt Injection | 使用者訊息不當更高優先指令；最後由 server 驗證硬限制與輸出 | CK-T28 |
| Demo 遭濫用 | chat API 限流、次數／token／成本上限，錯誤不洩漏內部訊息 | 429／大量請求 |
| 難以讀懂誤導 | 明確成本狀態與非醫療用途，避免過度權威語氣 | 三角色與 UX 測試 |

## 2. 目前不需要的個資

不要求長者姓名、地址、電話、證件、生日、處方、藥名、病歷、病症、完整家庭背景或健康資料照片。第一版以合成使用者案例為主。使用者主動輸入敏感內容時，應避免回顯到 public logs 與公開分享；不把敏感內容保存為長期輪廓。

## 3. 分享與外部評審

- 建立分享前預覽完整內容，提醒「知道連結的人可閱讀」，不得預設勾選。
- 建立匿名唯讀快照，不應把公開分享 URL 變成原聊天的編輯／接續通道。
- 高熵 token 儲存其 hash；擁有者獨立持有撤銷能力，設定實際過期／刪除流程。
- 原始對話即使只用假名仍可能有可辨識資訊，不能把程式自動去識別當作無風險保證。
- 提交 PDF 之前，用無痕視窗測試共享、過期、撤銷與 404；不得讓評審得到含個資的後台。
- 留存期限初步提案見 `docs/api-and-data-contracts.md`，**未經批准前不視為正式資料處理政策**。

## 4. 上線前最低檢查

HTTPS、HttpOnly/Secure/SameSite cookie、CSRF／origin check、request schema validation、回應輸出 encoding、限流、模型 timeout 與安全錯誤、錯誤 log 遮罩、依賴風險檢查、環境變數權限、對話備份與刪除政策。這些都是計畫驗收項，現在未跑任何掃描。

## 5. 學生與真實參與者

若要訪談長者或照護者，先準備同意方式、目的與資料保存／退出方式；避免蒐集非必要的診斷或處方資訊。公開報告可呈現匿名、取得同意的回饋；未取得真實受試者時，誠實寫「尚未驗證目標使用者」。

## 6. AI 助理不能聲稱的保證

「一定對高齡者健康」「符合特定疾病飲食治療」「與○○藥安全共食」「醫師／營養師已審核」「真實價格保證未超支」都不在本產品已驗證能力內。即使 Prompt 回答了，也應由伺服器和內容檢查移除不當保證。
